# 岔路：动态故事推演产品定义

> 导入一段故事，从原作中的一个关键决定开始，亲自走出另一条剧情线。

## 1. 要解决的问题

故事作者经常能感觉到某个关键决定还存在其他可能，却很难同时推演不同选择对人物、关系和后续冲突造成的连锁反应。通用聊天工具可以续写文本，但通常不会明确区分原始故事的既定事实、尚未接受的生成内容和作者已经确认的新剧情。

“岔路”服务拥有或正在创作故事的作者。它既接受短篇与章节，也允许作者从完整长篇中先定位一个焦点章节。产品把一次剧情推演做成有明确起点、连续状态和结束产物的游戏化体验，让 AI 提供可能性，让作者保留最终决定权。

## 2. 成功定义

一位第一次体验的作者能够在无需说明人员协助的情况下完成以下路径：

1. 粘贴短篇或章节、从长篇中选择焦点章节，或选择内置原创悬疑示例。
2. 检查并修正 AI 提炼的故事世界卡。
3. 从三个有解释的分歧候选中选择一个。
4. 以原故事主角身份完成四个场景回合。
5. 每轮选择建议行动或输入自定义行动，并决定接受或带修正意见重新推演。
6. 获得并复制一份可继续用于写作的新剧情线回顾。

完成这条路径比支持更多媒介、更多文件格式或无限生成更重要。

## 3. 核心体验

### 3.1 导入故事

- 支持直接粘贴文本。
- 支持读取 `.txt` 和 `.md` 文件。
- 支持 UTF-8 与 GB18030 长篇文本；完整原文在当前页面内建立章节导航，不整体发送给模型。
- 长篇作者先选择焦点章节或片段，再预览并编辑不超过 12,000 字的上下文包。
- 提供一个可立即开始的原创当代悬疑示例。
- 直接分析建议输入约 3,000～8,000 个汉字；长篇通过焦点导航自动装配有界输入。
- 当前进度自动保存在浏览器本地，无账号、数据库或跨设备同步。

### 3.2 确认故事世界

AI 从原始故事提炼一张可编辑的故事世界卡：

- **核心人物**：身份、目标和关键关系。
- **世界规则**：剧情分歧后仍不能随意改变的事实。
- **原始剧情**：到当前章节为止的关键事件。

作者修改后的内容才是后续推演的约束，原始模型结果没有更高权威。

### 3.3 选择分歧点

AI 给出三个分歧候选。每个候选包含：

- 原始故事中的关键时刻；
- 主角当时采取的行动；
- 为什么这个位置值得探索另一种选择。

作者选择其中一个，分歧点之前的原始剧情仍为既定事实；分歧点之后可以产生新剧情，但必须遵守世界事实。

### 3.4 动态故事舞台

每个场景回合按以下顺序进行：

1. 展示当前场景。
2. 提供三个会导向不同后果的建议行动，并允许作者输入一个自定义行动。
3. 根据行动生成推演草案。
4. 展示状态变化与简短推演依据。
5. 作者选择“接受并继续”，或输入一句修正意见后重新推演。

重新推演不会推进回合，也不会污染已接受的剧情状态。只有作者接受的场景才会成为新剧情线的一部分。

### 3.5 新剧情线回顾

接受四个场景回合后进入回顾页，展示：

- 新剧情线梗概；
- 四次关键选择与直接结果；
- 与原始剧情线的主要差异；
- 主角目标、人物关系和风险的变化；
- 仍未解决的冲突；
- 推演过程中始终遵守的关键世界事实。

作者可以一键复制 Markdown，不做项目发布或公开分享。

## 4. AI 的职责与边界

AI 负责：

- 从原始故事提出可供作者校正的结构化理解；
- 发现高价值的分歧候选；
- 根据主角行动和已接受剧情状态生成推演草案；
- 在长篇仍处于当前页面时，用焦点及之前的少量原文证据核对人物与世界事实；
- 说明可公开展示的因果依据，而不是暴露模型思维链；
- 基于已接受回合生成新剧情线回顾。

作者负责：

- 修正故事世界卡；
- 选择分歧点和主角行动；
- 接受或拒绝推演草案；
- 对最终结果负责。

模型输出错误时，产品必须明确报错并允许重试，不能用缓存结果假装本次调用成功。内置示例只是预填原始故事，也应走真实模型链路。

## 5. 剧情状态

每次推演使用明确的结构化状态，而不是仅依靠聊天记录。最小状态包括：

- 已确认的故事世界卡；
- 选定的分歧点；
- 主角当前目标与处境；
- 关键人物状态；
- 人物关系；
- 现有风险；
- 未解决冲突；
- 已接受回合。

一次模型返回分为“场景文本”“建议行动”“状态变化”“更新后的剧情状态”和“推演依据”。服务端必须验证结构后才交给前端。具体决策见 [ADR-0001](./adr/0001-use-explicit-structured-story-state.md)。长篇只在浏览器中导航并发送有界上下文的决策见 [ADR-0002](./adr/0002-use-local-long-form-navigation.md)。

## 6. 页面与视觉

产品只需要四个主要页面或阶段：

1. 导入故事；
2. 故事世界卡与分歧候选；
3. 动态故事舞台；
4. 新剧情线回顾。

视觉采用当代悬疑文字冒险氛围：克制的深色背景、清晰的长文排版、场景转场、选择卡片、状态变化和剧情时间线。视觉效果服务于阅读与决策，不实时生成场景图片。

## 7. 错误与恢复

以下状态必须有明确反馈：

- 未输入故事或内容过短；
- 文件格式不支持或读取失败；
- 模型请求超时或失败；
- 模型返回结构不完整；
- 修正后重新推演失败；
- 本地存在未完成的推演记录。

模型错误应保留作者当前输入和已接受状态，并提供重试；不得让失败请求推进回合。用户可以清除本地记录并重新开始。

## 8. 隐私与演示访问

- 短篇原文或长篇模式中可见的上下文包需要发送给所配置的模型服务，必须在导入区域明确告知作者。
- 完整长篇只在当前页面内存中存在；它不整体上传、不写入 `localStorage`，刷新后需要重新导入。
- 产品服务端不持久化保存原始故事或生成内容。
- 浏览器本地保存仅用于恢复当前体验，作者可以主动清除。
- 线上演示使用一个提交给评审的访问码；模型密钥只存放在服务端环境变量中。

## 9. 明确不做

- 自动理解、总结整本长篇或构建全书故事圣经；
- 无限场景回合；
- 实时场景图片；
- 账号、云端项目库或多人协作；
- 公开分享与读者游玩链接；
- 完整平行分支树；
- PDF、Word、EPUB 导入；
- 原作者文风模仿承诺；
- 用缓存结果冒充实时模型生成。

## 10. 建议技术形态

在没有既有代码的前提下，建议采用一个 TypeScript 全栈 Web 应用：同一项目承载界面与服务端模型接口，浏览器使用本地存储保存推演记录，服务端使用环境变量保存模型密钥与演示访问码，不引入数据库。只集成一个真实文本模型；供应商与具体模型在开始实现前依据已有密钥确定，不做多模型切换。

## 11. 九小时时间分配

| 时间 | 目标 |
| --- | --- |
| 0:00–0:45 | 固定数据结构、提示约束与原创悬疑示例 |
| 0:45–1:45 | 完成访问、导入和四阶段视觉骨架 |
| 1:45–3:00 | 打通故事世界卡与分歧候选的真实模型调用 |
| 3:00–5:30 | 打通四回合生成、状态提交、自定义行动和修正重做 |
| 5:30–6:15 | 完成回顾、Markdown 复制和本地恢复 |
| 6:15–7:15 | 补齐等待、失败、重试、清除和移动端基础体验 |
| 7:15–8:00 | 部署、访问码与线上主路径冒烟验证 |
| 8:00–9:00 | README、提交说明、最终验证和五分钟录屏 |

任何阶段超时，优先删除装饰性动画和非核心设置，不删除真实模型调用、作者确认、状态提交或最终回顾。

## 12. 验收标准

- [ ] 使用内置示例可以通过真实模型得到故事世界卡和三个分歧候选。
- [ ] 作者对故事世界卡的修改会约束后续生成。
- [ ] 作者可以选择建议行动，也可以输入自定义行动。
- [ ] 每轮推演展示状态变化和简短推演依据。
- [ ] 修正重做不增加已接受回合数，也不修改已接受状态。
- [ ] 接受四个回合后生成完整的新剧情线回顾。
- [ ] 回顾可以复制为 Markdown。
- [ ] 刷新页面后可以恢复当前推演，且可以主动清除。
- [ ] 模型失败时保留输入与状态，并可以重试。
- [ ] 线上体验不暴露模型密钥，访问码可正常使用。
- [ ] README 如实标注真实能力、限制、模型依赖和运行方式。
- [ ] 线上主路径经过至少一次从导入到回顾的完整人工验证。

## 13. 五分钟录屏结构

1. **0:00–0:35｜问题与选择**：作者不是缺少续写按钮，而是缺少能保持事实一致、又把决定权交还给自己的剧情推演工具。
2. **0:35–1:05｜范围**：说明目标用户、章节级输入、四回合边界和主动不做的内容。
3. **1:05–3:35｜完整演示**：内置示例、校正故事世界卡、选择分歧点、自定义行动、查看状态变化、修正重做、接受回合。
4. **3:35–4:10｜最终产物**：展示新剧情线回顾并复制 Markdown。
5. **4:10–4:40｜AI 与工程**：展示结构化剧情状态、草案与接受状态的分离，以及错误恢复。
6. **4:40–5:00｜完成边界**：如实说明当前可用、没有实现和下一步优先事项，并给出实际投入时间。

## 14. 提交时必须如实说明

- **真实可用**：以最终线上人工验证为准逐项列出。
- **Mock 或缓存**：默认没有；如果后来加入，必须明确指出具体位置和原因。
- **尚未完成**：以验收清单未勾选项为准，不能用计划语气包装成现有能力。
- **下一步**：优先验证更多作者样本下的世界事实提炼和长期一致性，再考虑长篇检索、分支树或分享能力。
- **实际投入**：记录真实时间，不把等待模型或部署的时间隐藏掉。
