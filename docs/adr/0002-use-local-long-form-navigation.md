# ADR-0002：长篇蓝本先在浏览器中导航，再发送有界上下文

## 状态

接受

## 背景

现有产品把一篇短篇或章节直接发送给模型，分析输入上限为 12,000 字。实际测试蓝本约 15.1 MB、761 万字符，包含约 2450 个章节标题，并使用 GB18030 编码。把整本书塞进一个请求会突破模型上下文、请求体和浏览器存储边界，也会让模型难以分辨用户真正想改写的时空位置。

可选方案包括：直接提高输入上限；在服务端持久化整书并建立向量库；导入时批量调用模型生成全书层级摘要；或者先在浏览器中解析长篇结构，让作者选定焦点章节，只发送一个有界上下文包。

## 决策

长篇蓝本只在当前浏览器页面中解码和建立章节导航，不写入应用服务端或浏览器持久化存储。作者先选择焦点章节或片段，应用再构建不超过现有分析边界的上下文包。

焦点章节是故事锚点，不是唯一发送内容。上下文包优先保留完整焦点阅读单元，再在总计 12,000 字以内自动带入焦点前后各最多两个相邻阅读单元，并用距离标签明确区分前文、焦点和后文。

推演阶段可以从当前页面仍持有的长篇蓝本中附带少量原文证据，但检索范围不得晚于焦点章节，避免把原始剧情线后续结果当作替代剧情必须发生的未来。作者确认过的故事世界卡仍是推演的规范事实来源。

首个实现支持 UTF-8 与 GB18030 文本、章节识别、超长章节切片、焦点导航和有界原文证据。全书模型摘要、嵌入检索和服务端书库不进入本次范围。

## 后果

- 15 MB 级长篇可以导入并导航，而不会被整体发送给模型。
- 作者必须明确选择故事发生位置，产品不会声称已经理解整本书。
- 刷新页面后长篇索引需要重新导入，但已经确认的故事世界卡与剧情状态仍可恢复。
- 全局人物弧线和跨卷设定仍可能遗漏；未来如需改善，应新增可审计的故事圣经构建流程，而不是静默扩大上下文。
